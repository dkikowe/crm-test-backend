# Salespace — API CRM с MongoDB Atlas

Node.js + Express + TypeScript + Mongoose + Zod. Клиенты, сделки, задачи и демо-пользователи хранятся в MongoDB. Фронтенд: [crm-test-frontend](https://github.com/dkikowe/crm-test-frontend).

## Локальный запуск

Нужны Node.js **22 LTS**, npm и MongoDB Atlas (или MongoDB replica set с поддержкой транзакций).

```bash
git clone https://github.com/dkikowe/crm-test-backend.git
cd crm-test-backend
npm ci
cp .env.example .env
```

Заполните `MONGODB_URI` в `.env` своей строкой подключения, затем:

```bash
npm run dev
```

API: [http://localhost:4000](http://localhost:4000). Проверка соединения: [GET /health](http://localhost:4000/health). При использовании nvm: `nvm install && nvm use`.

Настоящий `.env` не включён в Git. Если он уже настроен локально, **не перезаписывайте** его копированием примера. Не передавайте URI в переменные `NEXT_PUBLIC_*`.

| Переменная        | Назначение                           | Локальное значение                       |
| ----------------- | ------------------------------------ | ---------------------------------------- |
| `PORT`            | Порт Express                         | `4000`                                   |
| `FRONTEND_URL`    | Единственный разрешённый CORS origin | `http://localhost:3000`                  |
| `MONGODB_URI`     | Секретная строка подключения Atlas   | Свой URI из Atlas                        |
| `MONGODB_DB_NAME` | Отдельная база CRM                   | `salespace_crm`                          |
| `SEED_DEMO_DATA`  | Инициализация пустой базы            | `true` или `false`; по умолчанию `false` |

Имя базы задаётся через `MONGODB_DB_NAME`, даже если URI содержит другой путь. Для совместимости с текущим кластером Atlas допустимы 1–38 латинских букв, цифр, `_` и `-`. Пользователю БД нужны права чтения/записи и создания коллекций/индексов в выбранной базе. В Atlas Network Access должен быть разрешён IP компьютера или сервера API. Спецсимволы логина и пароля в URI должны быть URL-encoded. TLS-проверка не отключается.

Сервер открывает HTTP-порт **после** подключения и инициализации БД. Если соединение не установлено, запуск завершается ошибкой; скрытого перехода на память нет. `/health` выполняет ping MongoDB и возвращает `503`, если база недоступна. URI и пароль не выводятся в логи.

## Данные и первый запуск

При `SEED_DEMO_DATA=true` в полностью пустые коллекции CRM один раз записываются 3 пользователя, 15 клиентов, 12 сделок и 10 задач из `src/data/seed.ts`. Вся инициализация выполняется в транзакции. В `_crm_meta` создаётся маркер `seed-v1`.

Повторный запуск не сбрасывает изменения и не восстанавливает удалённые записи. Если в любой CRM-коллекции уже есть данные, начальное заполнение пропускается. Не включайте seed для базы с рабочими данными. Для учебной CRM после первого запуска можно установить `SEED_DEMO_DATA=false`.

| Пользователь  | ID          | Роль     | Права              |
| ------------- | ----------- | -------- | ------------------ |
| Александр Ким | `u-admin`   | Админ    | Все записи         |
| Алия Садыкова | `u-rop`     | РОП      | Все записи         |
| Данияр Омаров | `u-manager` | Менеджер | Только свои записи |

Демо-записи распределены между пользователями. Менеджер первоначально видит 5 клиентов, 4 сделки и 3 задачи. Даты seed рассчитываются при первой инициализации, сроки задач — по `Asia/Almaty`; позже они не сдвигаются.

**Демо-вход не заменяет настоящую аутентификацию:** клиент передаёт `X-User-Id`, который можно подменить. Используйте учебные данные. Пароли, регистрация и S3 не реализованы.

## Архитектура

```text
src/
├── app.ts                   # Express, CORS, зависимости
├── server.ts                # подключение БД, HTTP, корректное завершение
├── config.ts                # проверка окружения без вывода секретов
├── domain.ts                # сущности и этапы
├── validation.ts            # входящие JSON-схемы Zod
├── database/
│   ├── models.ts            # Mongoose-схемы и индексы
│   └── connection.ts        # соединение, первый seed, health, закрытие
├── data/seed.ts
├── routes/                  # HTTP → валидация → сервис
├── services/                # права, владельцы, связи, статистика
├── middleware/              # демо-аутентификация и JSON-ошибки
└── repositories/
    ├── interfaces.ts        # асинхронные контракты + транзакции
    ├── mongo.ts             # Mongoose, преобразование _id ↔ id
    └── memory.ts            # изолированный адаптер для обычных тестов
```

Слои: `routes → services → repositories`. API сохраняет строковые `id`; в MongoDB они являются `_id`. В JSON нет внутренних полей Mongoose. `createdAt` хранится строкой ISO для совместимости с фронтендом.

Все изменяющие операции сервиса — транзакции: проверка прав, проверка связей и запись выполняются согласованно. Записи сериализуются через служебный документ `_crm_meta/write-lock`, поэтому параллельное удаление клиента и создание сделки не оставят сделку без клиента. Это простой механизм для небольшой учебной CRM; при высокой нагрузке его следует заменить более узкой блокировкой. Сервис не зависит от Mongoose, сессия передаётся внутри адаптера через AsyncLocalStorage. Внутри транзакции запросы последовательны.

Индексы добавлены по владельцу, этапу, клиенту и сроку задач. При запуске создаются отсутствующие индексы; коллекции и существующие индексы не удаляются.

## API

Без входа доступны `/health` и `/users`. Все бизнес-маршруты требуют известный `X-User-Id`.

| Метод                | Путь           | Назначение                                     |
| -------------------- | -------------- | ---------------------------------------------- |
| GET                  | `/health`      | Ping БД, `200 {"status":"ok"}` или `503`       |
| GET                  | `/users`       | Список демо-пользователей                      |
| GET / POST           | `/clients`     | Список / создание клиента                      |
| GET / PATCH / DELETE | `/clients/:id` | Карточка / изменение / удаление                |
| GET / POST           | `/deals`       | Список / создание сделки                       |
| GET / PATCH          | `/deals/:id`   | Сделка / изменение этапа и других полей        |
| GET / POST           | `/tasks`       | Список / создание задачи                       |
| GET / PATCH          | `/tasks/:id`   | Задача / изменение и выполнение                |
| GET                  | `/stats`       | KPI, распределение по этапам, ближайшие задачи |

```bash
curl http://localhost:4000/clients -H 'X-User-Id: u-manager'
curl -X PATCH http://localhost:4000/deals/d-3 \
  -H 'X-User-Id: u-manager' \
  -H 'Content-Type: application/json' \
  -d '{"stage":"negotiation"}'
```

Этапы: `new`, `qualified`, `negotiation`, `payment`, `won`, `lost`.

Обязательные поля создания:

- Клиент: `name`, `company`, `email`, `phone`, `city`. По умолчанию `stage: "new"`, `source: "Сайт"`, `notes: ""`.
- Сделка: `title`, `clientId`, `amount` (тенге, 0–10¹², до двух знаков после запятой). По умолчанию `stage: "new"`.
- Задача: `title`, `dueDate` (`YYYY-MM-DD`). По умолчанию `clientId: null`, `completed: false`.
- У всех: `id`, `ownerId`, `createdAt`. ID и дата создания задаются сервером, `ownerId` по умолчанию равен ID текущего пользователя.

Менеджер видит и меняет только свои записи; чужой ID возвращает `404`. Админ и РОП видят всё. Владелец связанной сделки или задачи должен совпадать с владельцем клиента; при прямом создании записи для клиента коллеги передайте его `ownerId`.

Клиента с историей нельзя удалить или передать другому владельцу (`409`). Этап клиента и этапы его сделок независимы. PATCH изменяет только переданные поля, не сбрасывая остальные.

KPI: новые лиды — клиенты `new`; активные сделки — кроме `won`/`lost`; сумма воронки — сумма активных; конверсия — округлённое `won / (won + lost) × 100`, либо 0. Все показатели ограничены доступными пользователю записями.

Ошибки:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте заполненные поля",
    "details": [{ "field": "email", "message": "Некорректный email" }]
  }
}
```

`400` — данные, `401` — демо-пользователь, `403` — назначение/Origin, `404` — запись, `409` — конфликт, `413` — объём запроса, `503` — база недоступна. Неизвестные поля и пустые PATCH отклоняются Zod.

## Проверки и сборка

```bash
npm test
npm run build
npm start
```

Обычные тесты работают с изолированной памятью, без подключения к Atlas. Дополнительные интеграционные проверки настоящей MongoDB:

```bash
npm run test:mongo
```

Команда использует `MONGODB_URI` из `.env`, создаёт **отдельную случайно названную** базу `salespace_test_*` и удаляет только её после проверки. Нужны права на создание и удаление этой тестовой базы. Проверяются HTTP-контракты, роли, PATCH, связанные записи, откат транзакций, конкурентные записи, сохранение после переподключения и отсутствие повторного seed. Рабочая база не очищается.

## Деплой на Railway

1. Создайте сервис из **этого** репозитория.
2. **Root Directory = `.` (корень репозитория)**. Папки `api` здесь больше нет.
3. Node.js **22.x**, Build Command: `npm ci && npm run build`, Start Command: `npm start`.
4. В Variables добавьте `MONGODB_URI` (секрет), `MONGODB_DB_NAME=salespace_crm`, `SEED_DEMO_DATA=true` только для пустого учебного окружения, `FRONTEND_URL=https://ВАШ-ФРОНТ.vercel.app` без завершающего `/`.
5. `PORT` предоставляет Railway; сервер читает его и слушает `0.0.0.0`.
6. Разрешите в Atlas IP исходящих подключений вашего сервера. Создайте публичный HTTPS-домен Railway и задайте Healthcheck Path `/health`.
7. В Vercel для [фронтенда](https://github.com/dkikowe/crm-test-frontend) укажите `NEXT_PUBLIC_API_URL=https://ВАШ-API.up.railway.app`, затем передеплойте фронтенд.

CORS разрешает ровно один origin из `FRONTEND_URL`. Запросы без Origin (curl и health checks) допускаются. Не публикуйте `.env` и исходный файл ключей; на хостинге используйте Variables. Данные сохраняются после перезапуска или нового деплоя API.

Документация: [Mongoose — Connections](https://mongoosejs.com/docs/connections.html), [Transactions](https://mongoosejs.com/docs/transactions.html), [Atlas — Troubleshoot connection](https://www.mongodb.com/docs/atlas/troubleshoot-connection/), [Railway — Monorepo / root directory](https://docs.railway.com/deployments/monorepo).
