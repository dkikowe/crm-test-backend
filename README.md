# Salespace API

Express + TypeScript + Mongoose. Все аккаунты, клиенты, сделки, задачи, сессии и ограничения попыток входа хранятся в MongoDB. Тестовое заполнение отключено и удалено. Фронтенд: [crm-test-frontend](https://github.com/dkikowe/crm-test-frontend).

## Запуск

Node.js 22.x и MongoDB Atlas / replica set с транзакциями:

```sh
npm ci
cp .env.example .env
# Заполнить MONGODB_URI, не публикуя его
npm run dev
```

Если `.env` уже существует, не перезаписывайте его. Переменные:

| Переменная | Значение |
|---|---|
| PORT | 4000 локально; Railway предоставляет автоматически |
| FRONTEND_URL | http://localhost:3000 локально; https://crm-test-frontend-sandy.vercel.app на Railway |
| MONGODB_URI | Секретная строка MongoDB |
| MONGODB_DB_NAME | salespace_crm |

`FRONTEND_URL` — только origin, без пути и завершающего `/`. `SEED_DEMO_DATA` больше не используется: его можно удалить из Railway Variables. База не заполняется даже при старом значении `true`.

## Аккаунты и роли

Самостоятельная регистрация создаёт **менеджера**. Роль из JSON не принимается. Email нормализуется и защищён уникальным индексом. Доступ по `X-User-Id` полностью удалён.

| Роль | Права |
|---|---|
| manager | Только свои клиенты, сделки и задачи; назначение только себе |
| rop | Все записи отдела и назначение ответственных; без управления ролями |
| admin | Все записи и управление ролями сотрудников |

`GET /users` закрыт авторизацией; менеджер получает только себя. Последнего администратора нельзя понизить. Изменение роли отзывает сессии пользователя. Права проверяются сервером на каждом запросе.

Первый администратор регистрируется по одноразовому приглашению, которое создаёт оператор с доступом к базе:

```sh
npm run admin:invite -- admin@your-company.kz /absolute/private/admin-invite.txt
```

Команда разрешена только до появления первого администратора. В приватном файле будет ссылка на `/register` с токеном в URL-фрагменте; токен не попадает в HTTP URL и хранится в БД только как SHA-256. Приглашение действует 24 часа и используется один раз. При указанном email оно привязано к нему. Вместо email можно передать `-`: получатель приватной ссылки сам укажет адрес при регистрации. Пароль администратор задаёт сам. Файл приглашения не публикуйте в Git.

Пароли **не шифруются обратимо**: используется `scrypt` с уникальной случайной солью, N=131072, r=8, p=1, 64 байта результата. Исходный пароль не сохраняется, хеш не отдаётся в API. Сравнение — constant-time. Пароли регистрации/смены: 12–128 символов. Параметры соответствуют [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Сессия: случайный токен 256 бит, в БД только SHA-256, абсолютный срок 8 часов, TTL-индекс плюс явная проверка срока. Cookie: HttpOnly, SameSite=Lax, Path=/; на HTTPS — Secure и префикс `__Host-`. Фронтенд проксирует `/api/*` через свой домен, поэтому не требуется third-party cookie. Выход удаляет сессию из базы; смена пароля проверяет текущий пароль и отзывает все сессии.

Защита запросов: строгий CORS, обязательный `X-CRM-Request: 1` для изменений (защита от CSRF), `Cache-Control: no-store`, валидация Zod, лимиты входа в MongoDB (10 на email и 120 суммарно за 15 минут), максимум 2 одновременные операции scrypt на процесс. Ошибки входа не раскрывают существование email. Подтверждение email и восстановление по почте пока не реализованы; фиктивных кнопок для них нет.

## Удаление старого демо

Одноразовая миграция `retire-demo-v1` архивирует **только** старые seed ID (`c-1…c-15`, `d-1…d-12`, `t-1…t-10`, `u-admin`, `u-rop`, `u-manager`) в `_legacy_demo_archive` и удаляет их из рабочих коллекций. Архив недоступен через HTTP API. UUID-записи, созданные пользователями, сохраняются; записи с прежними владельцами передаются первому администратору при регистрации. Если пользовательские сделки/задачи связаны с тестовыми клиентами, миграция останавливается без частичного удаления — такие связи нужно разобрать отдельно. Повторный запуск не восстанавливает демо и не меняет рабочие записи.

## API

### Вебхук WhatsApp Cloud API

Callback URL для Meta: `https://crm-test-backend-production-7f1aec08.up.railway.app/webhooks/whatsapp`.
В Railway Variables задайте `WHATSAPP_VERIFY_TOKEN` (собственная случайная строка, та же в поле Verify token в Meta) и `WHATSAPP_APP_SECRET` (App Secret приложения Meta). Оба значения читаются только из окружения backend; в Git и frontend их добавлять нельзя. После изменения переменных примените новый deployment. Остальная CRM работает и без этих переменных; незаданный verify token даёт 403, незаданный App Secret — 503 на POST.

- `GET /webhooks/whatsapp`: при `hub.mode=subscribe`, правильном `hub.verify_token` и строковом `hub.challenge` возвращает challenge без JSON-кавычек, `Content-Type: text/plain`, статус 200. Иначе 403.
- `POST /webhooks/whatsapp`: проверяет `X-Hub-Signature-256: sha256=<64 hex symbols>` через HMAC-SHA256 от **исходных байтов тела**, сравнение constant-time. Отсутствующая, некорректная или неверная подпись даёт 401. Cookie CRM и `X-CRM-Request` не требуются: webhook подключён до CORS/CSRF/авторизации и общего JSON-парсера, остальные маршруты сохраняют защиту.
- После проверки подписи сервер возвращает `200 OK`. Только после события `finish` ответа, через `setImmediate`, разбирает JSON и логирует сводку: объект WhatsApp, количество entries/changes/messages/statuses/errors. Тексты сообщений, контакты, секреты и заголовки не логируются. Ошибка JSON или обработчика после ответа фиксируется отдельным безопасным сообщением и не меняет HTTP-ответ.
- Лимит тела — 1 МБ (превышение: 413); сжатые запросы не принимаются (415), чтобы подпись не проверялась по изменённому распаковкой телу.

Обработка пока выполняется в процессе сервера, без очереди, сохранения событий и дедупликации. Перезапуск после ответа может потерять событие; повторная доставка будет повторно залогирована. Это подходит для текущего этапа с логированием; перед добавлением бизнес-операций потребуется надёжная очередь/хранилище и идемпотентность.

`npm test` покрывает handshake, подписи по исходному UTF-8 (включая пробелы и escape-последовательности), подмену тела, отсутствие секретов, отправку ответа до обработки, ошибки обработчика и сохранение защиты CRM. Проверка протокола: [документация Meta](https://developers.facebook.com/docs/graph-api/webhooks/getting-started/).

Публичные: `GET /health`, `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`.

После входа:

- `GET /auth/me`, `POST /auth/password` (`oldPassword`, `newPassword`).
- `GET /users`; `PATCH /users/:id/role` (`role`) — только admin.
- `GET/POST /clients`, `GET/PATCH/DELETE /clients/:id`.
- `GET/POST /deals`, `GET/PATCH /deals/:id`.
- `GET/POST /tasks`, `GET/PATCH /tasks/:id`.
- `GET /stats` — статистика из реальных записей с ограничением по роли.

Регистрация: `name`, `email`, `password`, необязательный `inviteToken`. Вход: `email`, `password`. Используйте cookie jar и `X-CRM-Request: 1` для изменяющих запросов. Все ошибки — JSON `{ error: { code, message, details? } }`.

Этапы: `new`, `qualified`, `negotiation`, `payment`, `won`, `lost`. У клиента: имя, компания, email, телефон, город, источник, заметки, этап. У сделки: название, clientId, сумма в тенге, этап. У задачи: название, срок YYYY-MM-DD, необязательный clientId, completed. Для всех сервер задаёт id, ownerId, createdAt. Сумма: от 0 до 10¹², до двух знаков. Связанные записи должны иметь одного владельца. Клиента с историей нельзя удалить или передать другому владельцу (409).

Слои: routes → services → repositories. MongoDB и тестовый адаптер реализуют интерфейсы. Согласованные записи выполняются транзакциями с общей блокировкой `_crm_meta/write-lock` (подходит для небольшого отдела, не высоконагруженной системы).

## Проверки и деплой

```sh
npm test
npm run test:mongo
npm run build
npm start
```

`npm test` проверяет регистрацию, cookie, хеши, сессии, роли, CSRF, ограничения попыток и CRUD в изолированной памяти. `test:mongo` создаёт случайную базу `salespace_test_*`, проверяет миграцию, сохранение аккаунтов/сессий, уникальность email и транзакции, затем удаляет только эту тестовую базу. Рабочая база тестами не изменяется.

Railway: репозиторий backend, Root Directory `.`, Node.js 22.x, Build `npm ci && npm run build`, Start `npm start`, health `/health`. Переменные — таблица выше. Доступ Atlas должен быть разрешён серверу API. URI и секреты не передаются во фронтенд и Git. Старые демо-сессии после обновления перестают работать; пользователям нужно зарегистрироваться.

## Файлы клиентов (S3)

В Railway Variables добавьте **только на backend**:

```dotenv
S3_ENDPOINT=https://s3.ap-southeast-2.amazonaws.com
S3_REGION=ap-southeast-2
S3_BUCKET=test-learn-didar-bucket
AWS_ACCESS_KEY_ID=<ключ доступа>
AWS_SECRET_ACCESS_KEY=<секретный ключ>
```

Для временных AWS credentials дополнительно нужен `AWS_SESSION_TOKEN`. SDK также поддерживает IAM role. Для S3-совместимого сервиса замените endpoint, регион и бакет; при необходимости задайте `S3_FORCE_PATH_STYLE=true`. Без конфигурации CRM работает, загрузка возвращает понятную ошибку 503. Ключи не помещать в Git или `NEXT_PUBLIC_*`.

Бакет остаётся приватным, Block Public Access включён. В S3 → Permissions → CORS вставьте массив из `deploy/s3-cors.json`; для других доменов замените AllowedOrigins. `ExposeHeaders: ETag` обязателен для multipart. CORS не даёт публичного доступа к объектам.

Права серверного IAM principal: `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts` на `arn:aws:s3:::test-learn-didar-bucket/clients/*`; `s3:ListBucket` на сам бакет (нужен в том числе для корректного ответа 404 от HeadObject). При использовании SSE-KMS нужны отдельные разрешения на соответствующий KMS key. Не используйте корневые ключи AWS.

В Management → Lifecycle добавьте правило для `clients/`, которое отменяет незавершённые multipart uploads через 1 день. Оно страхует сбой между созданием multipart в S3 и записью UploadId в MongoDB. Не включайте удаление готовых объектов этим правилом. API каждые 5 минут очищает истёкшие незавершённые загрузки из S3 и MongoDB; окно загрузки — 24 часа.

Форматы и ограничения (1 МБ = 1024² байт): OGG/MP3 до 20 МБ; JPEG/PNG/WebP до 10 МБ; MP4 до 500 МБ. Видео всегда загружается частями по 8 МБ, последняя часть может быть меньше. Фронтенд получает свежую ссылку для каждой части, показывает прогресс и поддерживает отмену и повтор запроса. Бинарные данные идут напрямую из браузера в S3, не через Railway/Vercel.

Маршруты (все требуют сессии; POST также требует `X-CRM-Request: 1`):

- `GET /clients/:clientId/files` — список метаданных.
- `POST /clients/:clientId/files` — начало: `type` (audio/photo/video), `name`, `contentType`, `size`, необязательное `description`.
- `POST /clients/:clientId/files/:id/upload-url` — PUT URL для аудио/фото.
- `POST /clients/:clientId/files/:id/parts/:partNumber/url` — PUT URL части видео.
- `POST /clients/:clientId/files/:id/complete` — проверка и публикация; для видео `parts: [{partNumber, etag}]`.
- `POST /clients/:clientId/files/:id/abort` — отмена незавершённой загрузки.
- `GET /clients/:clientId/files/:id/view-url` — временный GET URL готового файла.

Каждая ссылка выдаётся после проверки текущего владельца клиента; менеджер видит только своих, РОП и администратор — всех. Сервер назначает `ownerId`, `uploadedBy`, UUID и ключ `clients/{clientId}/{type}/{uuid}`. Метаданные и описание хранятся в коллекции `files`, ссылки не сохраняются в базе. Клиент с файлами не удаляется и не передаётся другому владельцу.

Upload URL действует 300 секунд; view URL — 900. Выданная ссылка является bearer-доступом до истечения срока; logout не отзывает уже выданный URL. PUT подписан с точным Content-Length; одиночные загрузки и завершение multipart используют `If-None-Match: *`, чтобы ранее выданный URL не заменил сохранённый объект. До статуса ready сервер сверяет размер, MIME, сигнатуру контейнера, для видео — номера/размеры/ETag всех частей. Это проверка формата, не антивирус и не полное декодирование; воспроизведение зависит от кодеков браузера.

`npm test` дополнительно проверяет лимиты, чужие файлы, подписи URL, завершение/отмену и multipart. `npm run test:mongo` проверяет сохранность метаданных и индексы files в отдельной временной базе.
